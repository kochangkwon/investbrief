## Phase 1 — 측정 인프라 (최우선: 이것 없이는 개선 효과 판정 불가)

### P1-1. KOSPI 벤치마크 수집 폴백 + 백필 🔴

**문제:** `theme_alert_candidates.kospi_at_alert`가 751건 중 162건(22%)만 채워짐.
`_fetch_kospi_close()` → `fetch_last_close("KS11")` → 네이버 지수 API가 자주 실패.
알파(시장 대비 초과수익) 측정이 불가능한 상태.

**구현:**
1. `app/services/theme_alert_service.py`의 `_fetch_kospi_close()`에 폴백 추가:
   - 1차: 기존 `price_collector.fetch_last_close("KS11")`
   - 2차(1차 None 시): `daily_briefs.domestic_market` JSON에서 최신 `kospi.close`를 읽는다
     (`select(DailyBrief).order_by(DailyBrief.date.desc()).limit(1)` — 브리프의 값은
     "전일 종가"이므로 알림 시점 기준으로 의미가 맞음). DB 조회용 세션은
     `async_session()`으로 자체 생성.
   - 두 소스 모두 실패 시 None 유지 + `logger.warning`.
2. 백필 스크립트 `scripts/backfill_kospi_at_alert.py` 신규:
   - `kospi_at_alert IS NULL`인 후보 행에 대해, `theme_alerts.sent_at` 날짜의
     `daily_briefs.domestic_market.kospi.close`(해당일 없으면 직전 브리프)를 채운다.
   - 같은 로직으로 `kospi_return_30d/60d/90d`도 `sent_at+N일`의 브리프 종가로 재계산.
   - dry-run 출력(채울 건수) 후 `--apply` 플래그로만 실제 UPDATE.
3. `theme_alert_tracker.py`의 KOSPI 조회(`_fetch_kospi_on_or_before`)에도 동일 폴백 적용.

**완료 기준:** 백필 후 `kospi_at_alert` 채움률 ≥ 90% (2026-03-25 이후 브리프 존재 구간).
신규 알림은 100% 채워짐. `tests/test_kospi_fallback.py`: 폴백 순서·실패 시 None 검증.

### P1-2. 월간 리포트에 알파 표기

## Phase 2 — 수집 확대 (재료가 입구에서 유실되는 구멍)

### P2-1. DART 공시 페이징 + 전일 공시 포함 🔴

**문제:** `get_today_disclosures`가 `page_count=100` 1페이지만 조회(DART 일 공시 수백 건),
스캔이 08:10이라 당일 공시가 거의 없음 → 공시발 감지 이력 0건/387건.

**구현:** `app/collectors/dart_collector.py`
1. 페이징: 응답의 `total_page`를 읽어 최대 5페이지(500건)까지 루프. 페이지 간
   `asyncio.sleep(0.2)`. 예외 시 수집분까지만 반환.
2. `get_today_disclosures(target_date, include_previous_day: bool = False)` 파라미터 추가:
   True면 직전 영업일(주말·공휴일 건너뜀 — `theme_scan_runs`의 마지막 scan_date 활용
   또는 단순히 target_date-1이 주말이면 금요일로) 공시도 함께 조회해 합친다.
3. `theme_radar_service._scan_single_theme`의 DART 호출을 `include_previous_day=True`로.
   중복 방지: 기존 `detected_stocks` 선점 로직과 rcept_no 기준 dedup 유지.

**완료 기준:** 스캔 로그에 `DART 공시 수집: N건` N>100 확인. 2주 내 `[공시]` 출처
감지 1건 이상 발생 여부 모니터(발생 없으면 키워드 매칭 방식 재검토 이슈 등록).
`tests/test_dart_paging.py`: 페이징 병합·전일 포함 로직 단위 테스트(HTTP는 mock).

2. 기존 키(`institution_net/foreign_net`)는 호환 위해 최신 1일치로 유지하되,

### P2-3. 발굴(discovery) 코퍼스 확장

**문제:** 주간 테마 발굴 입력이 하루 20건의 거시 뉴스(증시/코스피/금리/환율)뿐 —
섹터 초기 테마가 입력에 등장하지 않음.

**구현:** `app/services/theme_discovery_service.py`
1. `discover_themes()`에서 브리프 아카이브에 더해, **활성 테마 키워드 상위 빈도
   뉴스 제목**을 보조 코퍼스로 추가: `_gather_theme_news` 재사용은 결합도가 높으므로,
   간단히 `news_collector._fetch_naver_news`를 섹터 고정 키워드 리스트
   (예: `["반도체 장비", "2차전지 소재", "방산 수주", "조선 수주", "제약 임상",
   "로봇", "원전", "전력기기", "화장품 수출", "게임 신작"]` — 상수로 정의,
   운영하며 조정)로 각 10건 수집해 `news_titles`에 `[섹터]` 접두어로 추가.
2. 프롬프트 입력 상한(현 600줄) 내에서 거시 400 + 섹터 200으로 배분.

**완료 기준:** 주간 발굴 로그의 입력 뉴스 수 증가 확인. 발굴 결과에 섹터 테마
등장 여부 4주 관찰.

## Phase 3 — 판정 품질

### P3-1. 교차 테마 가드 재설계 (역선택 해소) 🔴

**문제:** 복수 테마 매칭 제목을 **전 테마에서 제외** → HBM 대형 수주처럼 강한
재료일수록 여러 테마에 걸려 버려지는 역선택.

**구현:** `app/services/theme_radar_service.py`
1. `_find_multi_theme_titles` 반환을 "차단 집합"에서 "제목→매칭 테마 수" 맵으로
   확장하지 말고, **차단 조건을 이원화**한다:
   - (a) 제목에 광범위 기사 마커가 있으면 전 테마 차단(현행 유지 목적의 본질):
     `_BROAD_ARTICLE_MARKERS = ("관련주", "수혜주", "대장주", "테마주", "목표주가",
     "추천주", "유망주", "정리", "총정리", "리포트")` 중 1개 이상 포함 AND 복수 테마 매칭.
   - (b) 마커가 없는 복수 테마 매칭 제목은 차단하지 않고 **대표 테마 1개에만 배정**:
     해당 제목이 매칭된 키워드 수가 가장 많은 테마(동률이면 테마 id 낮은 쪽).
     구현: `_assign_primary_theme(title→{theme_id: matched_kw_count})` 순수 함수 신규,
     `scan_all_themes`에서 산출해 `_scan_single_theme(banned_titles=...)` 대신
     `allowed_titles_by_theme` 형태로 전달(다른 테마에 배정된 제목은 그 테마에서 skip).
2. `tests/test_cross_theme_guard.py` 갱신: 기존 4케이스 유지(광범위 리포트 픽스처는
   마커 "리포트"로 여전히 차단됨을 확인) + "HBM 수주 단독 기사 → 대표 테마 1곳에만
   살아남음" 케이스 추가.

**완료 기준:** 테스트 통과. 배포 후 [cross_theme_guard] 로그에서 차단 건수 감소·
배정 건수 표기.

### P3-2. 종목당 다중 기사 판정 (첫 기사 편향 해소)

**문제:** 종목당 최초 발견 기사 1건으로만 Claude 판정 — 약한 기사가 먼저 잡히면
강한 재료도 NO. NO 3일 윈도우(T4)와 결합 시 강재료 최대 3일 지연.

**구현:** `app/services/theme_radar_service.py`
1. `detected_stocks[code]`에 `alt_news: list[dict]` (최대 2건) 추가 — 같은 종목이
   다른 제목의 뉴스에서 재발견되면 append (제목 dedup).
2. 대표 기사 선정: `제목에 종목명 포함` > `pub_date 최신` 순으로 1건 선택해 검증.
3. 1차 판정이 **NO**이고 `alt_news`가 있으면, 그중 1건(같은 우선순위 규칙)으로
   **1회만** 재검증. YES면 채택(headline 등 대표 기사 교체). 재검증도 NO면 NO 기록.
   미판정(None)은 재검증하지 않고 기존 미판정 처리 유지.
4. Claude 비용 상한: 후보당 최대 2콜. `[verify]` 로그에 `retry_yes=N` 카운트 추가.

**완료 기준:** `tests/test_selection_fixes.py`에 대표 기사 선정 순수 함수 테스트 추가
(선정 로직은 `_pick_primary_news(info) -> dict` 순수 함수로 분리해 테스트).

### P3-3. 공휴일 신선도 동적 보정

**문제:** 월요일만 72h 확장 — 화요일 공휴일 다음 수요일 등은 24h라 연휴 뉴스 유실.

**구현:** `app/services/theme_radar_service.py::_gather_theme_news`
- 고정 `weekday()==0` 분기 대신: 직전 `ThemeScanRun.scan_date`(completed)를 조회해
  `gap_days = (오늘 - 직전 scan_date).days`를 구하고
  `freshness_hours = max(설정값, gap_days * 24)`로 계산.
  직전 run이 없으면 현행 로직 유지. DB 조회 실패 시 현행 로직 폴백.
- 월요일 하드코딩 분기는 제거(위 공식이 주말 gap=3일 → 72h를 자연 포함).

**완료 기준:** 로그의 `기준 Nh`가 연휴 다음날 자동 확장되는지 확인.
단위 테스트: gap 계산 순수 함수 분리 후 3케이스(평일/주말후/연휴후).

## Phase 4 — 운영 루프 완성

### P4-1. 피처 검증 분기 재검증 (영구 동결 해소)

**문제:** `.feature_validation_done` 마커 생성 후 재검증이 영원히 없음 — 국면이
바뀌어도 신호 고정.

**구현:** `app/services/scheduler.py::_feature_validation_check`
1. 마커 존재 시 즉시 return하지 말고, 마커 내용(ISO 날짜)을 읽어
   `90일 경과 시` 재검증 실행 → 신호 갱신 → 마커 날짜 갱신.
2. 재검증 결과 신호 구성이 변했으면 텔레그램 공지(추가/제거된 피처 명시),
   같으면 "신호 유지" 로그만.
3. 게이트(고유 60일 등)는 재검증에도 동일 적용.

**완료 기준:** 마커 날짜 조작 테스트(90일 전 날짜 기입 → 실행됨), 텔레그램 문구 확인.

### P4-2. 같은날 복수 테마 중복 알림 표시

**문제:** 같은 날 같은 종목이 2개 테마로 각각 알림(이력 30건) — 수신자 입장 중복.

**구현:** `theme_radar_service.scan_all_themes`에서 당일 이미 알림된 종목 코드 집합을
테마 간 공유(모듈 스코프 아닌 로컬 dict 전달). `_send_theme_alert` 메시지에서 해당
종목에 `(중복: 테마명)` 표시만 추가 — 기록(ThemeScanResult/스냅샷)은 양쪽 유지
(측정 데이터는 보존, 표시만 정리). P3-1의 대표 테마 배정이 먼저 대부분 해소하므로
**P3-1 배포 2주 후에도 중복이 남으면** 착수 (조건부 항목).

### P4-3. (보류 — 별도 승인 후) 장중 스캔 추가

D+1 후행 구조(R1) 완화책으로 13:00 KST 스캔 1회 추가가 가능하나, Claude 비용
약 2배 + 알림 피로 증가. **본 지시서 범위에서 구현하지 말 것.** P1 완료 후 알파
측정이 가능해지면, 08:10 알림의 시점별 성과를 보고 별도 결정한다.
