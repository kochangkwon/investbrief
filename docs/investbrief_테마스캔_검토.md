## 2. 실질 문제

### 🔴 2-1. 키워드당 "최신 10건" 고정 — 활발한 키워드일수록 커버리지가 좁아짐

`_gather_theme_news()` → `_fetch_naver_news(keyword)`는 **display=10 기본값**을 그대로 씁니다 (`sort=date`, 따옴표 정확구문 검색).

- 스캔당 뉴스 상한 = 65키워드 × 10건 = 650건
- **문제는 분포**: "HBM"처럼 하루 수십 건 나오는 키워드는 08:10 시점 **최신 10건 = 새벽 몇 시간치**만 커버 → **전일 장중에 나온 재료 기사가 창 밖으로 밀려 유실**됩니다. 반대로 한산한 키워드("케어푸드")는 10건이 며칠치를 커버(신선도 필터가 자름).
- 즉 **테마가 뜨거울수록(뉴스가 많을수록) 수집 커버리지가 나빠지는 역설**입니다. 신선도 필터(24h)는 있는데 그 24h를 채울 수집량이 없습니다.

**권고:** 라디르 스캔 경로에서만 `display=30~50`으로 상향 (백필 경로는 이미 display=100 사용 중 — 인프라는 검증됨). 호출 수는 동일(키워드당 1회)이고 응답 크기만 늘어납니다.

### 🔴 2-2. NO 판정이 기록되지 않음 — "YES는 14일 캐시, NO는 0일 캐시"

`_verify_and_persist_detections()`는 **YES만 ThemeDetection에 저장**합니다. NO 판정 종목은 아무 기록이 없으므로:

- 지속 이슈 종목(예: 매일 기사가 나오는 대형주)이 **매일 다시 Claude 검증**됩니다 — 스캔당 최대 테마×30 후보 순차 호출로 6.6~11.9분(실측)이 걸리는 주요 원인이자 반복 비용.
- 같은 종목·같은 이슈에 대해 **어제 NO, 오늘 YES 플립**이 가능한데(비결정적 LLM 판정), 이를 감지·측정할 데이터 자체가 없습니다.

**권고:** NO 판정도 `verdict` 컬럼과 함께 저장하고 중복 윈도우를 짧게(예: 3~5일) 적용. 플립율도 공짜로 측정 가능해집니다.

### 🔴 2-3. Claude 장애 시 그날 감지가 통째로·조용히 소거됨 (fail-closed × 재시도 없음 × 순차)

`_verify_theme_match()`는 rate limit / timeout / 파싱 실패를 전부 **NO로 강등**(fail-closed)하며, `ai_verifier._call_raw()`에는 **재시도가 없습니다** (429 재시도는 키움 쪽에만 구현됨). 검증은 순차 호출이므로:

- 스캔 중반에 rate limit이 걸리면 **이후 모든 후보가 조용히 NO 처리** → 그날 알림이 "감지 0건"으로 나가고, 사용자는 장애인지 무재료인지 구분 불가.
- 스캔 완료 메시지에도 검증 실패 카운트가 노출되지 않습니다(로그에만 남음).

**권고:** (a) `rate limit`/`timeout` 사유는 1~2회 지수 백오프 재시도, (b) 검증 실패 건수를 스캔 완료 텔레그램 메시지에 표기 ("검증 실패 N건 — 판정 보류"), (c) 실패 종목은 NO가 아니라 "미판정"으로 다음날 재시도.

### 🔴 2-4. 종목당 "첫 번째 기사 1건"으로만 판정 — 판정이 기사 도착 순서에 의존

`detected_stocks`는 `stock_code` 기준 **최초 등장 뉴스 1건**만 보관하고, Claude 검증도 그 1건으로만 합니다. 순서는 "키워드 순서 × 네이버 최신순"이라는 사실상 임의 기준입니다.

- 같은 날 A종목에 [약한 스침 기사, 강한 수주 기사]가 있으면 — 약한 기사가 먼저 잡히는 순간 **NO로 탈락**하고 강한 기사는 검증 기회조차 없습니다.
- 2-2와 결합하면: 다음날 기사 순서가 바뀌어 YES가 되는 등 판정이 불안정해집니다.

**권고:** 종목당 뉴스를 최대 2~3건 수집해 가장 최신(또는 제목에 종목명이 있는) 기사를 우선 검증하거나, 1차 NO 시 다른 기사로 1회 재검증.

## 3. 주간 테마 발굴(discovery) 문제

### 🟠 3-1. 발굴용 정규식이 영문 시작 종목명을 구조적으로 배제 (radar와 불일치)

```python
# theme_discovery_service.py — 한글 시작만 허용
STOCK_NAME_PATTERN = re.compile(r"([가-힣][가-힣A-Za-z0-9]{1,14})")
# theme_radar_service.py — 영문/한글 시작 모두 허용 (수정됨)
STOCK_NAME_PATTERN = re.compile(r"([A-Za-z가-힣][A-Za-z가-힣0-9&]{1,14})")
```

radar는 "LG, SK, HD, KT&G, POSCO 등 대형주 매칭" 주석과 함께 수정됐는데, **discovery의 빈도 분석은 옛 패턴 그대로**입니다. LG에너지솔루션·SK하이닉스·HD현대일렉트릭·POSCO홀딩스 등 영문 시작 종목은 "언급 빈도 TOP 10"에 절대 오를 수 없습니다.

또한 빈도 분석의 `if len(name) <= 2: continue`는 주석("단음절 차단")과 달리 **2글자도 차단** — 기아(2자) 등이 배제됩니다.

### 🟠 3-2. 발굴 코퍼스가 하루 20건의 거시 뉴스 — 니치 테마 발굴에 구조적 한계

발굴 입력은 `daily_briefs.news_raw`인데, 실측 **최근 30개 브리프 전부 정확히 20건**(상한)입니다. 그 20건의 출처는 "증시·코스피·금리·환율" 4개 거시 키워드 검색 + 경제 RSS 4개(각 5건)입니다. 공시도 하루 5건만 입력됩니다.

즉 주간 발굴은 **거시·시황 헤드라인 600건으로 섹터 테마를 추론**하는 구조라, 섹터 전문지에만 실리는 초기 테마(발굴의 본래 목적)는 입력에 등장하지 않습니다. 현재 테마 대부분이 반도체·로봇 등 이미 거시 뉴스에 오른 대형 테마인 것과 일관됩니다.

**권고:** 발굴 입력에 섹터 키워드 검색(예: 산업별 5~10개 고정 키워드) 또는 활성 테마 키워드의 수집 결과를 재활용해 코퍼스를 넓히기.

## 5. 우선순위 권고

1. **radar 스캔의 `display`를 30~50으로 상향** — 뜨거운 키워드의 전일 장중 기사 유실 차단 (2-1). 코드 1줄.
2. **검증 실패(rate limit/timeout)에 재시도 + 스캔 완료 메시지에 실패 건수 표기** — 조용한 전멸 방지 (2-3).
3. **NO 판정 기록 + 단기 윈도우** — 반복 검증 비용 절감과 플립 측정 (2-2).
4. **discovery 정규식을 radar와 통일** (영문 시작 허용) + `<= 2` → `< 2` 수정 (3-1). 코드 2줄.
5. 종목당 검증 기사 선택 로직 개선 (2-4), 연휴 신선도 보정 (4-3), 발굴 코퍼스 확장 (3-2)은 그다음.

**한 줄 평:** 스캔 엔진의 상태 관리·중복 방지·가드는 잘 만들어져 있고 실측으로도 깨끗합니다. 문제는 **입구(뉴스 10건 제한)와 출구(NO 미기록·장애 시 조용한 소거)**에 있습니다 — 둘 다 작은 수정으로 고칠 수 있는 위치입니다.
